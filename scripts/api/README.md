# API-v3-Toolchain (`scripts/api`)

Node 24 (ESM). Tests: `cd scripts/api && npm test`.

## Ueberblick

1. **Sync** (taeglich per `.github/workflows/sync-tcgdex.yml`, siehe [Taeglicher Workflow](#taeglicher-workflow-daily-sync)): `sources/sync-tcgdex.mjs` spiegelt die TCGdex-Daten nach `sources/tcgdex`, `sources/sync-cardmarket.mjs` laedt Cardmarkets Einzelkarten-Katalog nach `sources/cardmarket/` und den Preisguide nach `.cache/cardmarket/price-guide.json` (nie committet). Der pokemontcg-Snapshot in `sources/pokemontcg` ist eingefroren.
2. **Matching** (`build-matching.mjs`): ordnet pokemontcg-Sets/-Karten den TCGdex-Sets/-Karten zu, schreibt `api/v3/reports/matching.{json,md}` und bricht bei Qualitaets- oder Paar-Drift ab (`--min-card-match 0.995 --fail-on-pair-drift`).
3. **Build** (`build-api.mjs`): erzeugt aus Quellen, Matching und der **eingefrorenen Registry** (`api/registry/`) die statische API unter `api/v3/` (`sets.json`, `cards/<set>.json`, `search-index.json`, `meta.json`) und ergaenzt die Registry nur additiv.
4. **Reports** (`api/v3/reports/`): `matching.*`, `learned-tables.json` (aus Paaren gelernte Ableitungstabellen; Aenderungen erscheinen im Diff) und `cardmarket-ids.json` (Cardmarket-Abdeckung je Set).

Cardmarket-IDs (`merge/cardmarket-ids.mjs`, Spec `docs/superpowers/specs/2026-11-13-cardmarket-api-design.md` §3): Quelle ist `sources/cardmarket/catalog.jsonl` (alle Pokémon-Singles, geladen von `sources/cardmarket-catalog.mjs`). Der Cardmarket-Feed liefert keine Nummern: `collectorNumber` kommt nur aus `sources/cardmarket/custom-sets/<expansionId>.json`, alle Nummernregeln greifen also nur dort. `cardmarket/` (Altformat) liest der Build nicht mehr. Stufen je Karte (erste eindeutige gewinnt): 1. Override, 2. custom-set (exakte Nummer inkl. Zusatz; `ids.cardmarketSource: "custom-set"`; widersprochene TCGdex-IDs anderer Nummern werden ersetzt, normale Drucke bekommen das Basisprodukt, gestempelte/Jumbo-Varianten behalten Zusatz-Drucke derselben Nummer; zwei Produkte zur selben Nummer -> keine Entscheidung, `customSets.ambiguous`), 3. TCGdex-ID mit den Pruefungen unten, 4. die Regeln unten, 5. leer. Danach die **Stabilitaetsregel**: Grundlage ist die zuletzt veroeffentlichte Ausgabe (`api/v3/cards`, Option `previousDir`); ein ueber Stufe 2-4 vergebener Stand (`ids.cardmarket` und Varianten-IDs; custom-set seit dem Formatwechsel-Schutz ebenfalls, z. B. wenn ein neues Produkt mit gleicher Nummer das custom-set mehrdeutig macht; ein heute anders entscheidendes custom-set gewinnt, bewusst entfernen per Override `null`) bleibt, wenn heute keine Stufe ihn liefert oder eine andere Stufe-3/4-ID entsteht (`stabilityKept`, Quelle bleibt die von gestern). Er aendert sich nur, wenn das Produkt aus dem Katalog verschwindet (`stabilityDropped`), Stufe 1-2 entscheidet oder TCGdex selbst (gestern und heute Quelle TCGdex) eine andere ID liefert; haelt heute eine andere Karte das Produkt per TCGdex, entfaellt die gestrige ID (`stabilityConflicts`), eine heutige Regel-ID weicht dagegen (`displaced`). Eine gestrige reine TCGdex-ID kommt nur zurueck, wenn heute gar keine Stufe eine ID liefert und sie heute nicht geteilt ist (nie gegen eine heutige Korrektur); laut custom-set falsche IDs kommen nie zurueck (`stabilityDropped` mit `reason` `product-gone`, `custom-set`, `shared-tcgdex-id`). custom-set-Widersprueche gelten auch fuer Karten ohne eigenen custom-set-Treffer, sofern das custom-set ihre Nummer fuehrt (`customSets.dropped`); gestempelte/Jumbo-Varianten tragen nie das Basisprodukt, wenn die Karte einen normalen Druck hat. Die Herkunft der Mehrheits-Evidenz steht in `expansionMismatch.sets[].evidenceSource` (`tcgdex`, `previous`, `mixed`). Der Regressionstest gegen echte Daten laeuft nur mit `CM_REGRESSION=1 npm test`. Fehlt die TCGdex-ID, sucht der Build in der Expansion (= `ids.cardmarket` des Sets bzw. des TCGdex-Untersets) ein Pokémon-Single mit gleicher Nummer (ohne fuehrende Nullen, Gross/Klein egal) und gleichem Namen (ohne `[...]`-Zusaetze, Diakritika, Satzzeichen und Cardmarkets `Lv.<n>`; `★` = `Gold Star`). Ohne Nummerntreffer zaehlt nur ein Produkt ohne `collectorNumber`, wenn es das einzige dieses Namens in der Expansion ist. Gibt es mehrere gleichnamige Produkte, entscheiden die Angriffs- und Faehigkeitsnamen: die letzte `[...]`-Klammer des Cardmarket-Namens (ohne reine Zahlen) muss als Menge genau den EN-`attacks`/`abilities`-Namen der Karte entsprechen (normalisiert, Reihenfolge egal); genau ein solches Produkt ohne Nummer wird genommen (gilt auch fuer die Korrektur geteilter IDs und die Expansionspruefung). Genau ein Kandidat wird eingetragen (`ids.cardmarket: [id]`, `ids.cardmarketSource: "matched"`); mehrere Kandidaten, ein schon von TCGdex belegtes Produkt oder dasselbe Produkt fuer zwei Karten bleiben leer. Eine eindeutige TCGdex-ID wird nie ueberschrieben. Teilen sich mehrere Karten dieselbe TCGdex-ID (`duplicateTcgdexIds` im Report), nimmt eine Karte den strengen Treffer (genau ein Produkt mit gleicher Nummer und gleichem Namen, nie nur per Name), sofern das Produkt keiner anderen Karte gehoert: `ids.cardmarket` = [Treffer, ...nicht geteilte TCGdex-IDs], `ids.cardmarketSource: "corrected"`, Original in `ids.cardmarketTcgdex`; geteilte `variants[].cardmarketId` werden durch den Treffer ersetzt, nicht geteilte bleiben. Ohne strengen Treffer bleibt die TCGdex-ID. `api/v3/reports/cardmarket-ids.json` fuehrt je Set `cards`, `tcgdex`, `matched`, `missing`, `ambiguous` und die betroffenen `cardId`s; die CLI druckt die Summen. Der Suchindex traegt die primaere Produkt-ID als `cm` (`primaryCardmarketId`, gleiche Regel im Frontend: erste ungestempelte Variante mit `cardmarketId`, sonst erste Variante mit `cardmarketId`, sonst `ids.cardmarket[0]`; Jumbo-Varianten (`size: "jumbo"`) kommen zuletzt: ungestempelt und nicht Jumbo, sonst nicht Jumbo, sonst ungestempelt, sonst irgendeine; Karten nur mit Jumbo-Variante, z. B. mep-Museum oder svp-500, behalten deren ID).

Expansionspruefung (gleiches Modul, Report-Abschnitt `expansionMismatch`, CLI-Zeile "Cardmarket-Expansionspruefung"): Expansion eines Sets = Zuordnungsdatei (`"<setId>": expansionId` in `cardmarket-overrides.json`, `ids.cardmarketSetSource: "override"`), sonst `ids.cardmarket` von TCGdex, wenn die Expansion im Katalog steht (`merge-set.mjs`; den alten `tracker.json` gibt es nicht mehr). Sonst (auch bei `null`) wird sie nur abgeleitet, wenn >= 80 % der Karten mit IDs (heutige TCGdex-IDs, sonst die veroeffentlichten) ein namensgleiches Produkt in genau einer Expansion haben (`ids.cardmarketSetSource: "derived"`, Original in `ids.cardmarketTcgdexSet`, z. B. tk1a, np, bwp); sonst bleibt der Wert, das Set steht in `setsWithoutExpansion` und bekommt keine Regel-IDs. Je Karten-ID wird das Produkt im Katalog gesucht und sein Name nachsichtig verglichen (zusaetzlich Kurz-Tags wie `[GL]`/`[G]` als Text, ohne `Basic `, ohne ` - Untertitel`). Passt der Name nicht, ersetzt der Lueckentreffer in der Expansion der Karte die ID (`ids.cardmarketSource: "corrected-expansion"`, Original in `ids.cardmarketTcgdex`, Varianten mit); ohne Treffer wird sie entfernt, wenn das Produkt in einer fremden Expansion liegt (`dropped-mismatch`), sonst bleibt sie (`kept-mismatch`). Namensgleiche Produkte fremder Expansionen (Stempel-, Ball-Varianten) bleiben; Sets ohne gueltige Expansion werden nur gemeldet (`no-set-expansion`).
**Wichtig – Namensregeln gelten jetzt fast ueberall:** Weil der Katalog keine Nummern hat, sind in allen Expansionen ohne custom-set alle Produkte "ohne Nummer". Die Regeln "eindeutiger Name", Angriffsnamen, Energie-Symbol, Left/Right und Reihenfolge greifen also in jeder Expansion (frueher nur dort, wo die abgeleiteten Nummern fehlten). Schutz vor falschen Links bei Sonder-/Alt-Art-Drucken gleichen Namens (SIR, Full Art, Nachdrucke): Ein Name zaehlt nur, wenn er in der Expansion genau einmal vorkommt; sonst entscheiden nur eindeutige Angriffsnamen; die Reihenfolge nur bei exakt gleicher Anzahl Karten/Produkte und passendem Nachbar-Offset (ohne Nachbarn: IDs hoechstens 50 auseinander); sonst bleibt die Karte leer (Test "name-only rules need unique evidence"). Bereits veroeffentlichte IDs schuetzt die Stabilitaetsregel.

Zusatzregeln fuer Luecken (gleiches Modul, Report-Abschnitt `rules`, CLI-Zeile "Cardmarket-Regeln"; Reihenfolge: Override, TCGdex, obige Regeln, dann diese):
- **Oversize** (`oversizeExcluded`, Liste `oversizeExcludedProducts`): Produkte mit dem Klammer-Token `[Oversized]` (Gross/Klein egal) sind nie Kandidaten, auch nicht fuer Korrekturen. "Jumbo" in Angriffsnamen zaehlt nicht. Cardmarket fuehrt die meisten Oversize-Drucke ohne Marker; deshalb greifen die Reihenfolge-Regeln nur bei exakt gleicher Anzahl (ein zusaetzliches, unmarkiertes Produkt verhindert die Zuordnung).
- **Energie-Symbol** (`energySymbol`): Findet die Karte nichts, gilt ein einzelner Energie-Buchstabe in Klammern mitten im Namen als ausgeschrieben (`[G]` Grass, `[R]` Fire, `[W]` Water, `[L]` Lightning, `[P]` Psychic, `[F]` Fighting, `[D]` Darkness, `[M]` Metal, `[Y]` Fairy, `[N]` Dragon, `[C]` Colorless): "Bubbly [W] Energy" = "Bubbly Water Energy". Nicht vor der Angriffsklammer ("Nidoran [F] [...]" bleibt Nidoran ♀). Gleiche Eindeutigkeitsregeln wie oben.
- **Left/Right** (`leftRight`) und **Reihenfolge** (`ordered`): je Expansion und normalisiertem Namen, nur wenn jede Karte dieses Namens noch offen ist (keine TCGdex-ID, kein Override, kein Treffer), alle gleichnamigen Produkte frei sind und **keines eine `collectorNumber` hat** (Expansionen mit Nummern nutzen diese Regeln nie) und die Kartennummern rein numerisch sind. Zwei Karten mit aufeinanderfolgenden Nummern und genau ein `[Left]`- und ein `[Right]`-Produkt gleichen Grundnamens: Left -> kleinere Nummer. Sonst bei genau gleich vielen Karten wie Produkten mit identischem Cardmarket-Namen (gleiche Angriffsklammer; abweichende Kartenangriffe verhindern es): aufsteigende Nummer <-> aufsteigende Produkt-ID. Andere Anzahl -> nichts, die Karten stehen in `stillMissing`. Zusaetzlich muss bei der Reihenfolge jede Produkt-ID zu einem naechsten Nachbarn darunter oder darueber passen (Produkt-ID - Kartennummer gleich dessen Offset, +-2; Nachbarn = Karten mit ID in dieser Expansion und Produkte mit rein numerischer `collectorNumber`); gibt es keine Nachbarn, duerfen die Produkt-IDs der Gruppe hoechstens 50 auseinanderliegen. Sonst nichts, gemeldet in `orderedRejected` (`expansionId`, `name`, `cards`, `products`; Zahl in `rules.orderedRejected`), z. B. ein spaeterer Nachdruck mit weit entfernter ID (bwp Snivy 279925/547296).
- **Versions-Suffix** (`versionSuffixSkipped`, je Expansion `versionSuffixSkippedByExpansion`): Nummern wie `4V2` oder `224a` bleiben bedeutungstragend (`4V2` ist nie Karte `4`, `H1` nie `1`); gezaehlt werden solche Produkte, die keine Karte bekommen hat.

Manuelle Zuordnung, zwei Ebenen:
1. **Ganze Expansion: Custom-Sets** (`sources/cardmarket/custom-sets/<expansionId>.json`: `{ expansionId, name, cards: [{ productId, collectorNumber }] }`, Standard `4`, hoehere Versionen `4V2`/`4V3`, Sonderdrucke `224a`, Holo `H1`; einmalig umgewandelt aus `scripts/cardmarket/custom-sets/1536|1537|1538|5241.mjs`, Test `test/cardmarket-regression.test.mjs`). Stufe 2, vorzuziehen, wenn eine Expansion viele unnummerierte oder Sonderprodukte hat. Eintraege fuer Produkte, die nicht (mehr) im Katalog stehen, meldet der Report (`customSets.missingProducts`).
2. **Einzelne Karten: `api/mappings/cardmarket-overrides.json`** (eingerueckt, Schluessel sortiert): `{ "_comment": "...", "<setId>/<cardId>": <cardmarketProductId> | null }`. Ein Override gewinnt vor TCGdex und allen Regeln (`ids.cardmarket = [id]`, `ids.cardmarketSource: "override"`, Original in `ids.cardmarketTcgdex`; `variants[].cardmarketId` fallen weg, damit die primaere ID die des Overrides ist); `null` entfernt die ID bewusst. Die ID muss im Katalog (`sources/cardmarket/catalog.jsonl`) stehen, sonst wird der Eintrag mit "WARNUNG cardmarket-overrides.json" ignoriert (ebenso unbekannte Karten). Nur gewarnt, aber uebernommen ("(Warnung, uebernommen)"): Produkt ausserhalb der Expansion des Sets bzw. des eigenen Untersets, kein Pokémon-Single (Kategorie != 51), `[Oversized]`-Produkt, dasselbe Produkt bei mehreren Override-Schluesseln, Produkt gehoert per TCGdex schon einer anderen Karte. Report: `overrides` (`applied`, `removed`, `warnings`), je Set `override`.

Arbeitsliste: `stillMissing` im Report fuehrt jede noch fehlende Karte (`cardKey` im Override-Format, `name`, `deName`, `set`, `expansionId`, bis zu 5 `candidates` aus freien Produkten der Expansion: gleicher Name, gleiche Nummer, gemeinsame Woerter; `hint` bei Verdacht auf Sonder-/Oversize-Druck: `same-name-unnumbered` = mehrere gleichnamige Produkte ohne Nummer, `id-outlier` = Produkt-ID weit ausserhalb des Hauptbereichs der Expansion). Vorgehen: Kandidat auf Cardmarket pruefen (Bild, Seltenheit, Preis), Eintrag in `cardmarket-overrides.json` ergaenzen, neu bauen. `stillMissingByExpansion` (Anzahl je Expansion, absteigend) zeigt, welche Expansionen von einem Custom-Set-Skript profitieren wuerden (viele offene Karten in einer Expansion -> Custom-Set statt vieler Overrides).

**HTML-Import** (`scripts/api/cardmarket/import-html.mjs`, Spec §6): Reparaturwerkzeug fuer Custom-Sets. Cardmarket-Suchseiten (Seitenquelltext, z. B. `...Products/Singles/<Set>?sortBy=collectorsnumber_asc&perSite=100`) von Hand speichern nach `.local/cardmarket-html/` (ignoriert, nie committen; das Werkzeug laedt nie selbst Seiten). Aufruf: `node scripts/api/cardmarket/import-html.mjs .local/cardmarket-html/<seite>.html … [--dry-run] [--force] [--set <setId>]`. Liest Expansion (`idExpansion`), Produkt-IDs (Bild-URL) und Nummern (Titel; fuehrende Nullen weg, `H1`, Buchstaben `224a`, Version `V2` aus dem Link -> `146V2`; V1/ohne Version = Basisnummer) und fuehrt sie in `sources/cardmarket/custom-sets/<expansionId>.json` ein: bestehende Eintraege und `lot: true` bleiben, neue Produkte werden angehaengt, abweichende Nummern zu schon eingetragenen Produkten werden nur gemeldet (Exit-Code 2; `--force` ersetzt sie). Danach laeuft die echte Zuordnung fuer die Sets der Expansion zweimal im Speicher (ohne/mit Import; veroeffentlichte `api/v3/cards` auf den TCGdex-Stand zurueckgesetzt, ohne Stabilitaetsregel, nichts wird nach `api/v3` geschrieben) und druckt geschlossene Luecken, weiter offene Karten und Widersprueche (Karte bekommt ein anderes Produkt). `--dry-run` schreibt nichts; `--set` nimmt zusaetzliche Sets in die Vorschau (z. B. abgeleitete Expansion). Danach `node scripts/api/build-api.mjs` fuer die eigentliche Ausgabe.

Kartenbilder: oben in `images` strikt Englisch (TCGdex EN, sonst pokemontcg-Legacy-URL), Deutsch nur in `i18n.de.images`; `warnings.missingImages` zaehlt Karten ohne EN-Bild und ohne `i18n.de.images`.

Set-Logos und -Symbole: `sources/verify-assets.mjs` (im Workflow nach dem Sync, `continue-on-error`) prueft nur Set-Logos (en/de) und -Symbole aus `sources/tcgdex/assets-index.json` gegen assets.tcgdex.net, nie Kartenbilder, und fuehrt das Ergebnis in `sources/tcgdex/assets-verified.json` (`{ url: { status: ok|missing, checkedAt } }`). `ok` wird nie erneut geprueft, `missing` nach 7 Tagen, neue URLs einmal; je Asset erst `.webp`, `.png` nur wenn `.webp` fehlt. Netzwerkfehler, Timeouts sowie HTTP 401/403/408/429/5xx aendern nichts (bekannter Status bleibt, Unbekanntes bleibt unbekannt). Der Build gibt als fehlend verifizierte URLs nicht aus (oben greift die pokemontcg-Legacy-URL, `i18n.de.images.logo` entfaellt) und meldet `Assets: <ok> ok, <missing> fehlen` je Asset-Gruppe. Erneute Pruefung erzwingen: den Eintrag aus `assets-verified.json` loeschen. Etwa woechentlich aendert sich `checkedAt` der fehlenden Eintraege; der Sync committet das mit.

Ausgabeformat: `api/v3/cards/*.json` und `api/v3/search-index.json` sind kompakt (eine Zeile, `toCompactJson`); `api/registry/**`, `api/v3/sets.json`, `api/v3/meta.json`, `api/v3/reports/learned-tables.json` und `api/v3/reports/cardmarket-ids.json` sind eingerueckt (`toJson`). Beide mit sortierten Schluesseln und abschliessendem Zeilenumbruch.

Die Registry vergibt kanonische Set-IDs und Kartenschluessel. Sie ist die Grundlage der Zeilenschluessel in `db_collection` und darf sich daher nur additiv aendern.

Alt-App-Set-IDs ohne eigene Karten (z. B. `TCGDEX-swsh9.5tg` fuer die Trainer-Galerie aus `db_sets`/Uebersicht der alten App) stehen in `api/mappings/legacy-set-aliases.json` (`{ "<alias>": { "set": "<kanonische Set-ID>", "reason": "..." } }`). Der Build nimmt sie additiv in `aliases` des Zielsets auf (Registry und `api/v3/sets.json`); ein unbekanntes Zielset bricht ab, eine Kollision mit einem fremden Alias ist ein `RegistryInvariantError`. Einmal eingetragen bleiben sie eingefroren, auch wenn der Mapping-Eintrag spaeter fehlt.

## Taeglicher Workflow (Daily Sync)

Ein Workflow, `.github/workflows/sync-tcgdex.yml` ("Daily Sync"), laeuft taeglich um 02:00 UTC, als Rueckfall nochmals um 05:30 UTC (und manuell) auf `master`; Laeufe warten aufeinander (Concurrency `sync-tcgdex`). Ein zweiter Lauf mit gleichem Stand aendert nichts und committet nicht: TCGdex wird bei unveraendertem Upstream-Commit nicht neu gespiegelt, `sources/cardmarket/meta.json` bleibt bei gleichem Datenstand byte-gleich (`lastSuccess` = erster Erfolg mit diesem Stand), der Build ist idempotent und `prices/meta.json` aendert `generatedAt` nur bei geaenderten Preisen. Der alte Workflow "Build Cardmarket Data" ist entfallen; `cardmarket/` (Altformat) ist eingefroren und wird nicht mehr erzeugt. Die Tests unter `scripts/cardmarket/` (Altbestand bis zur Release-Umstellung) laufen nicht mehr in CI.

Schritte:
1. **Tests** (`npm test` in `scripts/api`).
2. **Sync TCGdex** (`sources/sync-tcgdex.mjs`); ein Fehler bricht den Lauf ab.
3. **Verify set assets** (`sources/verify-assets.mjs`, `continue-on-error`, 10 min).
4. **Sync Cardmarket** (`sources/sync-cardmarket.mjs`): Einzelkarten-Liste und Preisguide, je 120 s Timeout und 1 Wiederholung. Endet immer mit Exit 0, ausser bei Programmfehlern. Erfolg: `sources/cardmarket/catalog.jsonl` (nur bei Aenderung), `expansions.json`, `meta.json` (`consecutiveFailures: 0`) und `.cache/cardmarket/price-guide.json`. Ausfall (`failed`) oder unplausible Daten (`defective`): nur `meta.consecutiveFailures` steigt, der Preisguide-Cache wird geloescht. Die Plausibilitaet zaehlt **brauchbare** Zeilen, damit ein stiller Formatwechsel weder Preise leert noch custom-set-Entscheidungen kippt. Defekt ist: keine Einzelkarten; < 99 % der Kategorie-51-Zeilen mit ganzzahliger `idExpansion`/`idProduct`; < 80 % der Einzelkarten des letzten Erfolgs; < 99 % der Preiszeilen mit numerischer `idProduct`; < 80 % der brauchbaren Preiszeilen des letzten Erfolgs (`meta.prices` zaehlt nur brauchbare); mehr als max(200, 0,5 %) der Produkt-IDs des committeten `catalog.jsonl` verschwunden. Zusaetzlich im Build: faellt `cardsWithPrice` unter 80 % des veroeffentlichten `prices/meta.json`, bleiben alle Preisdateien unveraendert (Warnung "WARNUNG Preise"). `consecutiveFailures` bleibt nur erhalten, wenn der Lauf committet: scheitert danach ein anderer Schritt (TCGdex, Matching, Build, Push), wird nichts committet, und der naechste Lauf zaehlt wieder vom committeten Stand aus. Umgekehrt zaehlen zwei fehlgeschlagene Cardmarket-Downloads am selben Tag (02:00 und Rueckfall 05:30) doppelt.
5. **Matching-Pruefung** (`build-matching.mjs --min-card-match 0.995 --fail-on-pair-drift`) und **Regressionstests** gegen die frischen Quellen.
6. **Build** (`build-api.mjs`): Karten, Registry, Cardmarket-IDs, Preise, Reports. Ohne Preisguide von heute bleiben `api/v3/prices/*` und `prices/meta.json` unveraendert (Vortagespreise, altes Datum). Schreibt zusaetzlich `.cache/cardmarket/issue.json` (`{ open, title, body }`, `report/cardmarket-issue.mjs`).

   Reverse-Holo-Felder in `api/v3/prices/<setId>.json`: Eintraege enthalten `avgHolo` (`avg-holo`), `trendHolo`, `avg1Holo`, `avg7Holo`, `avg30Holo`, `lowHolo` nur, wenn die Karte plausibel einen Reverse-Druck hat (Cardmarket fuehrt -holo-Felder auch fuer Produkte ohne Reverse, z. B. base1). Regel (`hasReversePrint` in `merge/cardmarket-prices.mjs`): Hat die Karte Variantenangaben (`variants[]`, TCGdex), zaehlt nur eine Variante mit `type: "reverse"` (`holo`/`normal` allein genuegen nicht); ohne Variantenangaben entscheidet `avg-holo` > 0.
7. **Commit und Push**: ein Commit `chore: daily sync (TCGdex, Cardmarket)` mit `sources/tcgdex sources/cardmarket sources/SOURCES.json api/v3 api/registry`; Push mit Rebase, 2 Versuche. Ohne Aenderungen kein Commit.
8. **Weitergabe**: startet per `workflow_dispatch` (Ref `release`) "Promote Master to Dev and Release" (`propagate-master-to-dev-release.yml`), auch ohne Commit. Ein Fehlschlag ist nur eine Warnung; dann die Weitergabe manuell starten.
9. **Cardmarket-Issue** (`continue-on-error`): genau ein offenes Issue mit Label `cardmarket-mapping` und Titel "Cardmarket-Zuordnung prüfen". `open: true` und keins offen -> anlegen; schon offen -> nur Titel/Text aktualisieren, wenn sie sich geaendert haben (kein taeglicher Kommentar); `open: false` -> mit kurzem Kommentar schliessen. Ausloeser: neues/junges Set (nicht in der vorherigen `sets.json` oder hoechstens 60 Tage alt) mit < 80 % Abdeckung oder ohne ermittelbare Erweiterung, Override-/custom-set-Eintrag mit nicht mehr vorhandenem Produkt, 3 Cardmarket-Ausfaelle in Folge. Kleinere Luecken stehen nur in `api/v3/reports/cardmarket-ids.md`.
10. **Bei Fehlschlag** eines Schritts ohne `continue-on-error` (Tests, TCGdex, Matching, Regression, Build, Push, Programmfehler im Cardmarket-Schritt): nichts wird committet, Issue mit Label `upstream-sync` (neu oder Kommentar am offenen).

Neu starten: Actions -> "Daily Sync" -> "Run workflow" (Branch `release`; die Workflow-Definition kommt von `release`, ausgecheckt wird immer `master`). Ein zweiter Lauf am selben Tag ist unschaedlich: er laedt Cardmarket erneut, baut und committet nur Aenderungen. Nur die Weitergabe: "Promote Master to Dev and Release" manuell starten. Lokal nachstellen (aus dem Repo-Root): `node scripts/api/sources/sync-cardmarket.mjs`, dann `node scripts/api/build-api.mjs`; danach `.cache/cardmarket/issue.json` ansehen. Hinweis: Lokal kann der 120-s-Timeout bei sehr langsamer Leitung greifen (Datei ~14 MB); das ergibt `failed` und erhoeht `consecutiveFailures` in `sources/cardmarket/meta.json`, diese Aenderung dann verwerfen.

"Promote Master to Dev and Release" einmal von Hand starten, damit `release` die neuen Workflow-Dateien bekommt (Zeitplaene und Dispatch-Definitionen liest GitHub von `release`; bis dahin gelten dort noch die alten Dateien mit "Build Cardmarket Data"). 2. ## Registry-Drift beheben

### Was die Fehler bedeuten

- **`RegistryFrozenError`**: Der Build wuerde einen bestehenden Registry-Eintrag aendern oder entfernen (Set/Karte verschwunden, `pokemontcg`/`tcgdex`-Verweis geaendert, Schluessel entfernt, ...). Typische Ursache: TCGdex hat eine Karte/ein Set umbenannt, neu nummeriert oder entfernt. Jede Zeile der Meldung nennt `Set <id>` bzw. `Karte <set>/<cardId>` und das betroffene Feld (`alt -> neu`, `entfernt: <ref>`).
- **`RegistryInvariantError`**: Die Registry verletzt eine Invariante (Schluessel doppelt vergeben, Schluessel nur in Gross-/Kleinschreibung verschieden, TCGdex-Karte oder pokemontcg-ID mehrfach referenziert, Set-ID unzulaessig). Die Meldung nennt Set, Schluessel und beteiligte Karten.
- **`Registry-Karten ohne Quelle`** (Build-Fehler): Eine Registry-Karte hat weder eine pokemontcg- noch eine TCGdex-Karte mehr. Ausgabe: `<set>/<cardId> (pokemontcg ..., tcgdex <set>/<localId>)`.

Beide Fehler stehen in der CLI-Ausgabe von `node scripts/api/build-api.mjs` (`FEHLER: ...`), im CI-Log des Sync-Laufs und im automatisch angelegten Issue (Label `upstream-sync`). Es wird nichts committet, `api/` bleibt unveraendert.

### Korrigieren (reviewte manuelle Aenderung)

Die Registry ist die Wahrheit; ein Build aendert eingefrorene Werte nie selbst. Korrekturen sind bewusste, im PR reviewte Handedits:

1. **TCGdex-Verweis umhaengen** (z. B. Karte hat jetzt eine andere `localId` oder ein anderes Set): in `api/registry/cards/<set>.json` bei der Karte den Eintrag in `tcgdex` (`{ "set": "...", "localId": "..." }`) auf die neue Referenz setzen. Den alten Schluessel in `keys.tcgdex` stehen lassen (alte Schluessel loesen weiter auf dieselbe Karte auf) und den neuen ergaenzen.
2. **Karte stilllegen** (Karte existiert upstream nicht mehr): Eintrag nicht loeschen, sondern `tcgdex` auf `[]` setzen (und `pokemontcg` auf `null`, wenn auch dort weg). Die Karte erscheint dann nicht mehr in der API, der Schluessel bleibt aber reserviert. Ist das nicht moeglich, den Eintrag bewusst entfernen und im PR begruenden.
3. **Set-ID umbenannt** (TCGdex-Set-ID): in `api/registry/sets.json` das Feld `tcgdex` auf die neue ID setzen und die alte ID in `aliases` aufnehmen. Die kanonische Set-ID (Dateiname `cards/<set>.json`) bleibt.

Wirkung auf bestehende Sheet-Zeilen: **Schluessel bleiben unveraendert**, nur die Verweise (Refs) auf die Quellen aendern sich. Bestehende `db_collection`-Zeilen loesen weiter auf dieselbe kanonische Karte auf.

Der Build vergleicht gegen die Registry-Dateien im Arbeitsverzeichnis: Die reviewte Handaenderung wird damit der neue Vergleichsstand. Im PR die Abweichung und ihren Grund ausdruecklich nennen.

### Pruefen

1. `cd scripts/api && npm test` (inkl. Kompatibilitaetstests gegen die Sammlungsschluessel).
2. `node scripts/api/build-api.mjs` aus dem Repo-Root: Exit 0, danach `git status` ansehen.
3. Build ein zweites Mal ausfuehren: `git status` darf sich nicht weiter aendern (sauber/idempotent), `Registry-Aenderungen: 0`.
